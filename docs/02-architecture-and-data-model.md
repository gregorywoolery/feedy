# 02. Architecture and data model

## Runtime shape

Feedy is a Next.js App Router application with server-rendered data pages and client components for interactive sheets, filters, selection, deletion, downloads, and recent-project preferences. PostgreSQL is accessed through Drizzle ORM and `postgres.js`. Photo bytes can live on local disk or in the same PostgreSQL database.

The main source boundaries are:

| Path                     | Responsibility                                                                    |
| ------------------------ | --------------------------------------------------------------------------------- |
| `src/app`                | Pages, layouts, and HTTP route handlers                                           |
| `src/features`           | Dashboard, application shell, and side-sheet workflows                            |
| `src/entities/contracts` | Serializable records passed between layers                                        |
| `src/use-cases`          | Injected application workflows, queries, presentation mapping and export assembly |
| `src/server`             | Explicit dependency wiring and per-process export admission                       |
| `src/data-access`        | Drizzle queries and persistence transactions                                      |
| `src/lib/database`       | Environment resolution, client, and Drizzle schema                                |
| `src/lib/storage`        | Storage interface with local filesystem and PostgreSQL implementations            |
| `src/lib/validation`     | Zod input/query validation and image validation/normalization                     |
| `src/lib/export`         | PDF layout and filename generation                                                |
| `drizzle`                | Checked-in SQL migration and Drizzle metadata                                     |

Typical feedback creation follows this path:

```text
Feedback side sheet
  -> POST /api/feedback (multipart FormData)
  -> validate request fields and build a typed input
  -> createFeedbackUseCase
  -> confirm project
  -> validate/normalize images
  -> write photo bytes through PhotoStorage
  -> insert feedback + photo metadata in one DB transaction
  -> return the complete feedback record
```

If database persistence fails after photo files were written, the use case attempts to remove those newly written files.

## Data model

### `projects`

| Column        | Type           | Rules                                           |
| ------------- | -------------- | ----------------------------------------------- |
| `id`          | UUID           | Primary key, generated by PostgreSQL            |
| `name`        | varchar(160)   | Trimmed non-empty value, maximum 160 characters |
| `description` | text, nullable | Maximum 4,000 characters                        |
| `created_at`  | timestamptz    | Defaults to current time                        |
| `updated_at`  | timestamptz    | Defaults to current time                        |

Indexes support case-normalized project-name lookup and updated-time ordering.

### `feedback_items`

| Column            | Type        | Rules                                                          |
| ----------------- | ----------- | -------------------------------------------------------------- |
| `id`              | UUID        | Primary key, generated by PostgreSQL                           |
| `project_id`      | UUID        | Required project foreign key; low-level deletion is restricted |
| `project_version` | varchar(80) | Trimmed non-empty value, maximum 80 characters                 |
| `description`     | text        | Trimmed non-empty value, maximum 10,000 characters             |
| `created_at`      | timestamptz | Defaults to current time                                       |
| `updated_at`      | timestamptz | Defaults to current time                                       |

Indexes support project/date listing, version filtering, and created/updated sorting.

### `feedback_photos`

| Column              | Type              | Rules                                                        |
| ------------------- | ----------------- | ------------------------------------------------------------ |
| `id`                | UUID              | Primary key, generated by PostgreSQL                         |
| `feedback_id`       | UUID              | Required feedback foreign key; cascades on feedback deletion |
| `storage_key`       | text              | Unique opaque local-storage key                              |
| `original_filename` | varchar(255)      | Sanitized basename, non-empty                                |
| `mime_type`         | varchar(80)       | JPEG, PNG, or WebP only                                      |
| `size_bytes`        | integer           | 1 byte through 10 MiB                                        |
| `width`, `height`   | integer, nullable | Positive when present                                        |
| `sort_order`        | integer           | Zero or greater; unique within one feedback record           |
| `created_at`        | timestamptz       | Defaults to current time                                     |

`storage_key` points to bytes managed by the selected `PhotoStorage` adapter. The delete use cases remove feedback metadata transactionally, then clean up the corresponding stored bytes. Project deletion explicitly removes its feedback records inside one transaction before removing the project.

### `photo_objects`

| Column       | Type        | Rules                                  |
| ------------ | ----------- | -------------------------------------- |
| `key`        | text        | Primary key shared with photo metadata |
| `mime_type`  | varchar(80) | Supported normalized image type        |
| `bytes`      | bytea       | Normalized image bytes                 |
| `created_at` | timestamptz | Defaults to current time               |

This table is used only when `STORAGE_DRIVER=database`; it makes uploads durable on serverless deployments without requiring object-storage credentials.

## Dashboard query behavior

The dashboard keeps its view state in URL query parameters, so filtered views can be copied or refreshed. It supports:

- Search across project name, version, and feedback description
- Exact project and version filters
- With-photos and without-photos filters
- Inclusive start date and inclusive calendar end date interpreted consistently by the server
- Created, updated, project, or version sorting in either direction
- Page sizes of 10, 25, 50, or 100

Invalid or unsupported query values fall back to stable defaults. Search is limited to 200 characters before it reaches the repository.

The project detail view supports the same search, version/photo/date filters, sorting, pagination, and filtered export scoped to its project. Stored timestamps remain `timestamptz`; visible dates are formatted after hydration in the accessing browser's system time zone. PDF exports remain explicitly labeled UTC for portable records.

## API errors

Route handlers return structured JSON errors for invalid data, missing records, and failed operations. Validation errors include field-level messages used by the side sheets. The route handlers use the Node.js runtime because image processing, filesystem storage, and PDF creation depend on Node APIs.

## Enforced boundaries

Use cases depend on application-owned ports in `src/use-cases/ports.ts`. The server composition module supplies repositories, photo storage, normalization, PDF rendering and cleanup. Pages call application queries rather than assembling repositories directly. Photo URL presentation is outside persistence.

Route handlers validate JSON, multipart fields and route IDs before calling the application. Input types are derived from the Zod schemas so runtime validation and TypeScript contracts stay in sync. Use cases receive named, typed inputs and enforce business rules such as project existence, photo ownership and export limits. ESLint permits schema type imports in use cases but prevents runtime schema imports there.

`unknown` stays at untrusted boundaries such as JSON parsing, browser storage and error handling. A TypeScript type alone does not validate external data.

Metadata changes and pending photo deletions are committed together. `photo_cleanup_jobs` retains the storage key and adapter namespace until deletion succeeds. This is an explicit recovery protocol across independent storage systems, not a distributed transaction. Filesystem and database storage use the same protocol.
